## Codex 분석

- 힌트 수준(Codex 판정): 작은 힌트. `PriorityQueue`의 import와 빈 큐의 `peek()`·`poll()` 반환값, 배열 참조를 출력해 확인하는 방법을 안내했다.
- 복습 등급: B
- 등급 판정 근거: 16분에 설계를 확정하고 40분에 통과했다. 30분 목표를 10분 넘겼으며, 만료 시각을 이용자 수와 비교하는 실수로 첫 통과 전 오답이 발생했다.
- 목표 시간 달성: 아니오 (40분 / 30분)
- 첫 시도 성공: 아니오 (첫 통과 전 오답, 공식 오답 제출 횟수는 확인 대기)
- 공식 출제 의도 알고리즘: 문제 본문에 명시되지 않음
- Codex 추천 목표 알고리즘: 현재 시각에 반납할 수를 차감한 뒤 필요한 만큼만 증설하고 그 증설분의 만료 시각을 기록하는 선형 시뮬레이션
- 실제 풀이와 의도 알고리즘 비교: 현재 코드는 `[만료 시각, 증설 대수]`를 우선순위 큐에 넣어 가장 이른 만료를 확인한다. 만료 처리를 먼저 하므로 `serverCount`에는 현재 시간대에 사용할 수 있는 증설분만 남는다. 각 시간의 부족분만 추가하면 그 시간의 요구량을 충족하는 데 필요한 최소 대수를 쓰고, 일찍 증설하는 것보다 더 오래 유지할 수 있다.
- 코드 개선 포인트: `k`는 고정이고 각 시간대에 한 묶음만 추가하므로 만료 시각 `hour + k`는 추가 순서대로 증가한다. 따라서 FIFO 큐로도 충분하며, 이 문제처럼 시간 범위가 작으면 `expiring[hour]`에 그 시각에 반납할 대수를 바로 기록할 수 있다. `requiredServerCount == 0`인 항목은 기록을 생략할 수 있다.
- 클린 코드 예시:

```java
public int solution(int[] players, int m, int k) {
    int[] expiring = new int[players.length + k];
    int activeServers = 0;
    int totalAdded = 0;

    for (int hour = 0; hour < players.length; hour++) {
        activeServers -= expiring[hour];
        int needed = players[hour] / m;
        int added = Math.max(needed - activeServers, 0);
        activeServers += added;
        totalAdded += added;
        expiring[hour + k] = added;
    }
    return totalAdded;
}
```

- 풀이 후 새로 배운 점: `i`는 현재 시각이고 `players[i]`는 그 시각의 이용자 수다. 단위가 다른 두 값을 비교하면 컴파일은 되지만 만료 처리가 틀어질 수 있다.
- 다음 문제에 적용할 한 문장 규칙: 시간 비교는 `hour`, 수량 계산은 `playerCount`처럼 변수에 단위를 드러내고, 만료 직전과 만료 시각을 나란히 검증한다.
- 오류 분류: 구현·시간 관리
- 잘한 점: 만료 전에 필요한 서버 수를 계산하는 실수를 피했고, 같은 시간대 증설을 묶어 한 항목으로 관리했다. 최종 코드가 공개 예제 3개와 무작위 비교 2,000건에서 검증을 통과했다.
- 개선할 점: `k = 1`에 `players[0] = players[1] = 3`, `m = 3`인 입력에서 두 시간 모두 증설해야 하므로 정답은 2다. 만료 분기 직전에 현재 시각·다음 만료 시각·운영 대수를 찍으면 비교하는 값이 맞는지 확인하기 쉽다.
- 시간복잡도: 시간대 수를 `T`라 하면, 현재 코드는 시간대마다 최대 한 묶음을 추가하고 각 묶음은 `k`시간 안에 빠진다. 큐에 최대 `min(T, k)`묶음이 있으므로 전체 상한은 `O(T log(min(T, k) + 1))`이다. 만료 배열을 쓰는 개선안은 배열 초기화를 포함해 `O(T + k)`이며 `k ≤ T`이면 `O(T)`다.
- 공간복잡도: 기존 큐는 최대 `k`묶음으로 `O(k)`, 개선안 배열은 `O(T + k)`
