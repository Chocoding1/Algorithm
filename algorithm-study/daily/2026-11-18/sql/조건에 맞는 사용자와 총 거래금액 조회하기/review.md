## Codex 분석

- 힌트 수준(Codex 판정): 정답 쿼리 — 최초 쿼리의 `WHERE`·`GROUP BY`·`HAVING` 순서, 행 필터와 그룹 필터의 위치, `UGU.USER_ID = 집계결과.WRITER_ID` JOIN 조건을 설명하면서 완성된 쿼리를 제공함
- 복습 등급: C
- 등급 판정 근거: 목표 20분 안인 11분 30초에 최종 통과했고 작성한 서브쿼리·그룹 집계 방향은 유효했다. 그러나 `WHERE`와 `HAVING`의 역할 및 절 순서를 구분하지 못해 문법 오류가 발생했고, 올바른 JOIN 조건까지 포함한 완성 쿼리를 확인한 뒤 통과했으므로 독립 해결로 볼 수 없다.
- 목표 시간 달성: 달성 — 11분 30초 / 20분
- 첫 시도 성공: 아니요 — 첫 통과 전 오답 1회
- 핵심 문법: `INNER JOIN`·파생 테이블·`WHERE`·`GROUP BY`·`SUM`·`HAVING`·`ORDER BY`
- 결과 한 행의 단위: 완료된 거래 금액 합계가 70만 원 이상인 사용자 한 명
- 쿼리 데이터 흐름: `USED_GOODS_BOARD`에서 `DONE`인 게시글 행만 `WHERE`로 남기고, 작성자별로 묶어 가격을 합산한 다음 `HAVING`으로 70만 원 이상인 그룹만 남긴다. 이 집계 결과를 사용자 테이블과 연결해 ID·닉네임·총액을 출력하고 총액 오름차순으로 정렬한다.
- 중복·NULL·JOIN 카디널리티 확인: 게시글 테이블에서는 한 사용자가 여러 행이지만 서브쿼리의 `GROUP BY WRITER_ID` 후에는 사용자당 한 행이 된다. 이를 사용자 기본정보와 연결하므로 최종 결과도 사용자당 한 행이며 `DISTINCT`는 필요 없다. 사용한 연결·집계 컬럼은 문제에서 NULL 불가다.
- 정답 검증: 최종 쿼리는 완료 거래만 합산하고, 작성자 단위 총액 조건과 요구 컬럼·오름차순 정렬을 모두 반영해 공식 제출에 통과했다.
- 코드 개선 포인트: 내부 원본 테이블과 외부 파생 테이블에 모두 `UGB`를 사용해도 범위가 달라 문법상 문제는 없지만 읽기 어렵다. 원본 게시글은 `B`, 사용자별 집계 결과는 `S`처럼 역할을 구분하면 JOIN 조건과 컬럼 출처가 더 명확하다.
- 클린 쿼리 예시:

```sql
SELECT U.USER_ID,
       U.NICKNAME,
       S.TOTAL_SALES
FROM USED_GOODS_USER AS U
JOIN (
    SELECT B.WRITER_ID,
           SUM(B.PRICE) AS TOTAL_SALES
    FROM USED_GOODS_BOARD AS B
    WHERE B.STATUS = 'DONE'
    GROUP BY B.WRITER_ID
    HAVING SUM(B.PRICE) >= 700000
) AS S
    ON U.USER_ID = S.WRITER_ID
ORDER BY S.TOTAL_SALES;
```

원본 SQL은 사용자의 최종 통과 쿼리를 보존하기 위해 수정하지 않았다.

- 풀이 후 새로 배운 점: `WHERE`는 그룹을 만들기 전에 개별 행을 거르고, `HAVING`은 `GROUP BY`와 집계가 끝난 뒤 그룹을 거른다. 따라서 거래 상태는 `WHERE`, 사용자별 `SUM(PRICE)` 조건은 `HAVING`에 둔다.
- 오류 분류: 문법·필터·집계·JOIN 컬럼
- 다음에 적용할 규칙: 개별 기록에 묻는 조건은 `WHERE`, `SUM`·`COUNT`로 만들어진 그룹 결과에 묻는 조건은 `HAVING`에 쓰고, 절은 `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY` 순서로 읽는다.
