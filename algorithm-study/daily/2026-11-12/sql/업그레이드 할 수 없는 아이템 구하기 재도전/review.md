## Codex 분석

- 힌트 수준(Codex 판정): 없음
- 복습 등급: B
- 등급 판정 근거: 15분 목표 안인 7분에 이전 정답을 보지 않고 `NOT IN`의 `NULL` 문제를 직접 방지한 최종 쿼리로 첫 공식 제출에 통과했다. 다만 그 전에 작성한 `EXISTS` 조건의 방향이 틀렸으므로 관계의 부재를 표현하는 두 방식이 아직 완전히 안정적이지 않다.
- 목표 시간 달성: 달성 — 7분 / 15분
- 첫 시도 성공: 재도전 문제로 대상 아님
- 핵심 문법: `NOT IN`·`IS NOT NULL`·서브쿼리·`ORDER BY DESC`
- 결과 한 행의 단위: 자식 아이템의 `PARENT_ITEM_ID`로 한 번도 등장하지 않아 더 이상 업그레이드할 수 없는 아이템 한 개
- 쿼리 데이터 흐름: `ITEM_TREE`에서 `NULL`이 아닌 부모 ID 목록을 만든다 → `ITEM_INFO` 중 그 목록에 없는 아이템만 남긴다 → 아이템 ID 내림차순으로 정렬한다.
- 중복·NULL·JOIN 카디널리티 확인: 같은 부모가 여러 자식을 가질 수 있어 서브쿼리 결과가 중복될 수 있지만 `IN` 판정 결과에는 영향이 없다. `DISTINCT`는 정확성에 필요하지 않다. 반면 `NULL`이 하나라도 남으면 `NOT IN` 비교가 `UNKNOWN`이 될 수 있으므로 `IS NOT NULL` 필터는 반드시 필요하다.
- 정답 검증: 플랫폼 첫 공식 제출 통과. 출력 컬럼과 내림차순 정렬도 요구사항과 일치한다.
- 코드 개선 포인트: 현재 쿼리는 정답이다. `DISTINCT`를 제거해도 결과는 같으며, 관계 부재를 직접 표현하고 `NULL` 영향을 피하려면 아래처럼 작성할 수 있다.

```sql
SELECT INFO.ITEM_ID, INFO.ITEM_NAME, INFO.RARITY
FROM ITEM_INFO AS INFO
WHERE NOT EXISTS (
    SELECT 1
    FROM ITEM_TREE AS TREE
    WHERE TREE.PARENT_ITEM_ID = INFO.ITEM_ID
)
ORDER BY INFO.ITEM_ID DESC;
```

- 풀이 후 새로 배운 점: `NOT IN`을 사용할 때는 서브쿼리 결과의 `NULL`을 제거해야 한다. `NOT EXISTS`에서는 바깥 아이템을 부모로 가진 자식 행이 존재하지 않는지를 상관 조건으로 검사한다.
- 오류 분류: 관계 존재 여부 조건의 방향 오류 — 잘못된 `EXISTS` 시도 후 안전한 `NOT IN`으로 수정
- 다음에 적용할 규칙: “연결 행이 없는 원본 행”을 찾을 때는 먼저 `NOT EXISTS (연결 조건)`을 고려하고, `NOT IN`을 쓴다면 서브쿼리에 `NULL`이 들어올 수 있는지 반드시 확인한다.
