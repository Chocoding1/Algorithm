- 실제 풀이와 의도 알고리즘 비교: 처음에는 모든 토핑을 오른쪽 맵에 넣고, 절단 위치를 오른쪽으로 옮길 때 현재 토핑을 왼쪽 맵에 추가하고 오른쪽 맵에서 하나 제거했다. 오른쪽 개수가 0이면 키 자체를 삭제해 두 맵의 `size()`가 곧 양쪽의 토핑 종류 수가 되도록 유지했다.
- 풀이 전 사고와 실제 코드의 차이: 없음 — 회고에 적은 두 맵 갱신과 종류 수 비교를 그대로 구현함
- 정답을 보장하는 이유: `i`번째 반복이 끝난 뒤 왼쪽 맵은 `0..i`, 오른쪽 맵은 `i+1..끝`의 토핑만 정확히 나타낸다. 개수가 0인 오른쪽 키를 삭제하므로 각 맵의 크기가 실제 종류 수와 같고, 가능한 모든 절단 위치를 한 번씩 검사해 공평한 경우를 빠짐없이 센다.
- 핵심 엣지 케이스: 첫 조각 뒤에서 자르는 경우, 마지막 조각 앞에서 자르는 경우, 같은 토핑만 있는 경우, 오른쪽에서 특정 토핑의 마지막 하나가 이동해 키를 삭제해야 하는 경우
- 코드 개선 포인트: 현재 코드는 정확하고 시간복잡도도 최적이다. 다만 왼쪽에서는 종류 수만 필요하므로 빈도 맵 대신 `Set`을 사용하면 상태의 의미가 더 분명하다. 선언 타입도 구현체인 `HashMap`보다 `Map` 인터페이스로 두는 편이 유연하다. 빅오 개선은 아니다.
- 클린 코드 예시:

```java
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

// 프로그래머스 Lv.2
public class 롤케이크_자르기 {

    public int solution(int[] topping) {
        Map<Integer, Integer> rightCounts = new HashMap<>();
        for (int type : topping) {
            rightCounts.merge(type, 1, Integer::sum);
        }

        Set<Integer> leftTypes = new HashSet<>();
        int fairCuts = 0;

        for (int i = 0; i < topping.length - 1; i++) {
            int type = topping[i];
            leftTypes.add(type);

            int remaining = rightCounts.get(type) - 1;
            if (remaining == 0) {
                rightCounts.remove(type);
            } else {
                rightCounts.put(type, remaining);
            }

            if (leftTypes.size() == rightCounts.size()) {
                fairCuts++;
            }
        }

        return fairCuts;
    }
}
```

- 풀이 후 새로 배운 점: 빈도 맵에서 값이 0인 키를 남겨두면 `size()`가 실제 종류 수와 달라진다. 종류 수를 맵 크기로 판단할 때는 마지막 원소가 빠지는 순간 키도 삭제해야 한다.
- 다음 문제에 적용할 한 문장 규칙: **경계가 한 칸 이동할 때 양쪽 전체를 다시 세지 말고, 이동한 원소 하나만 양쪽 상태에 반영할 수 있는지 확인한다.**
- 복습에 포함할 학습 포인트: 절단 위치별 좌우 상태 불변식, 개수 0인 키를 삭제하는 이유, 두 맵을 사용해도 전체가 `O(N)`인 이유
- 오류 분류: 없음
- 시간복잡도: 평균 `O(N)` — 전체 빈도 구성과 절단 위치 순회에서 각 원소를 상수 번 처리함
- 공간복잡도: `O(K)` — 서로 다른 토핑 종류 수 `K`만큼 맵에 저장함
