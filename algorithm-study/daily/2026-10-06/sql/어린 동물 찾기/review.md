## Codex 분석 — 풀이 완료 후 작성

- 정답 여부: 프로그래머스 첫 제출은 통과했다. 다만 문제에서 요구한 `ANIMAL_ID` 순서를 최종 쿼리에서 `ORDER BY`로 명시하지 않아 SQL 의미상 결과 순서가 보장되지 않는다. 채점 데이터의 현재 반환 순서와 실행 계획에 기대어 통과한 것으로 볼 수 있으므로 정렬 조건까지 포함한 쿼리가 완전한 답이다.
- 쿼리 실행 순서와 각 절의 역할: `FROM ANIMAL_INS`가 동물 한 마리의 입소 정보를 한 행으로 읽고, `WHERE INTAKE_CONDITION != 'Aged'`가 조건을 만족하지 않는 원본 행을 제외한다. `SELECT ANIMAL_ID, NAME`은 남은 행에서 두 컬럼만 출력한다. 마지막 `ORDER BY ANIMAL_ID`가 있어야 결과 행의 표시 순서가 ID 오름차순으로 확정된다.
- 더 명확하거나 일반적인 작성법: MySQL에서는 `!=`와 `<>`가 모두 같지 않음을 뜻한다. `<>`는 SQL 표준 표기다. 정답 요구사항을 모두 명시하면 다음과 같다.

```sql
SELECT ANIMAL_ID, NAME
FROM ANIMAL_INS
WHERE INTAKE_CONDITION <> 'Aged'
ORDER BY ANIMAL_ID;
```

- `NULL`·중복·정렬에 미치는 영향: `INTAKE_CONDITION`이 `NULL`이면 `NULL <> 'Aged'`는 `TRUE`가 아니라 `UNKNOWN`이므로 해당 행도 `WHERE`에서 제외된다. 이 문제의 데이터 조건에서는 문제가 되지 않더라도 “Aged만 제외하고 NULL은 포함”하려는 일반 요구라면 `INTAKE_CONDITION <> 'Aged' OR INTAKE_CONDITION IS NULL`처럼 의도를 명시해야 한다. JOIN·집계·`DISTINCT`가 없으므로 입력 한 행은 결과에서 최대 한 행으로 유지되며, 같은 이름은 제거되지 않는다. `ORDER BY`가 없으면 출력 순서는 보장되지 않는다.
- 풀이 전 사고와 실제 쿼리의 차이: 풀이 전에는 ID 순 정렬이 필요하다고 정확히 적었지만 실제 쿼리에는 `ORDER BY ANIMAL_ID`가 빠졌다. 필터 조건과 출력 컬럼은 계획대로 구현했다.
- 이번에 새로 배운 내용: 화면에서 이미 정렬되어 보이거나 채점이 통과해도 `ORDER BY`가 없으면 SQL 결과 순서는 계약상 보장되지 않는다. 또한 일반 비교 연산자는 `NULL`을 참으로 판정하지 않으므로 포함 여부를 별도로 결정해야 한다.
- 다음 문제에 적용할 한 문장 규칙: 결과 순서가 요구되면 기본 저장·조회 순서를 믿지 말고 마지막에 `ORDER BY`를 명시하며, 비교 컬럼이 `NULL`일 수 있으면 `UNKNOWN` 처리까지 확인한다.
- 코드 개선 포인트: `ORDER BY ANIMAL_ID`를 추가하는 것은 단순 스타일 개선이 아니라 문제의 정렬 요구를 보장하는 정확성 수정이다. `!=`를 `<>`로 바꾸는 것은 이 문제에서 결과·성능 차이가 없는 표준 표기 선택이다.
