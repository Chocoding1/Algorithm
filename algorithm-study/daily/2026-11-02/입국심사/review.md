## Codex 분석

- 힌트 수준(Codex 판정): 정답 코드 — 배분 경우를 직접 만들지 않고 `T`분 동안 처리 가능한 인원을 합산하는 핵심 판정식, 이분 탐색 범위·갱신 규칙과 완성된 `solution` 코드를 대화에서 확인함
- 복습 등급: C
- 등급 판정 근거: 사람 배분을 직접 탐색하는 최초 접근의 경우의 수 병목은 인식했지만 시간에 대한 단조성으로 전환하지 못했고, 핵심 판정식과 완성 코드를 확인한 뒤 오답 1회를 수정해 통과함

- Codex 추천 목표 알고리즘: 결정 문제 `주어진 시간 안에 n명을 처리할 수 있는가`로 바꾼 매개변수 탐색
- 공식 의도 일치 여부: 일치(힌트 후)
- Codex 목표 일치 여부: 일치(힌트 후)
- 실제 풀이와 의도 알고리즘 비교: 최종 코드는 `right = 가장 빠른 심사 시간 × n`을 상한으로 두고, 각 `mid`에서 `sum(mid / time)`으로 처리 가능 인원을 계산해 최소 가능 시간을 찾으므로 의도와 일치함
- 풀이 전 사고와 실제 코드의 차이: 최초에는 심사대별 배정 인원 조합을 생성해 `max(배정 인원 × 심사 시간)`을 최소화하려 했다. 최종 구현은 배정을 직접 복원하지 않고 후보 시간 하나가 가능한지만 판정하므로 조합 탐색을 약 60회의 범위 축소로 바꿈
- 의도 알고리즘 추가 학습 이유: 최적의 배분 자체를 열거하기 어려워도 정답 후보가 가능한지 빠르게 판정할 수 있고, 후보가 커질수록 가능 상태가 유지되는 단조성이 있으면 정답 값에 이분 탐색을 적용할 수 있음을 익혀야 함
- 풀이 직후 확인한 의도 알고리즘:
  - 핵심 신호: 정답이 매우 큰 수의 범위에 있고, 시간 `T`가 충분한지 여부를 `O(times.length)`에 판정할 수 있으며, 가능 여부가 `불가능 → 가능`으로 한 번만 바뀜
  - 판정식: 심사대 `time`이 `T`분 동안 처리하는 사람은 `T / time`명이고, 합계가 `n` 이상이면 `T`는 가능한 시간임
  - 범위 갱신: 불가능하면 `left = mid + 1`, 가능하면 `mid`도 최소 정답일 수 있으므로 `right = mid`
  - 후보 하나의 판정 비용: `O(M)`, 여기서 `M = times.length`, 즉 심사대 개수. 후보 시간 `T`마다 모든 심사대의 `T / time`을 최대 한 번씩 계산함
  - 전체 복잡도: `O(M log(minTime × n))` — 후보 하나를 `O(M)`에 판정하고 시간 범위를 이분 탐색함
- 이분 탐색을 판단한 과정:
  1. 정답이 `모든 심사가 끝나는 최소 시간`이라는 하나의 정수 최솟값임을 확인함
  2. 심사대별 배분을 직접 만들면 경우의 수가 너무 커서 배분 자체를 탐색할 수 없음을 확인함
  3. 배분 대신 후보 시간 `T`를 고정하면 각 심사대가 처리할 수 있는 인원이 `T / time`으로 즉시 결정됨을 발견함
  4. `sum(T / time) >= n`이면 `T`가 가능하다는 판정식 `P(T)`를 만듦
  5. `P(T)`가 참이면 그보다 긴 시간도 항상 참이므로 결과가 `불가능 ... 불가능 | 가능 ... 가능`으로 단조적임을 확인함
  6. 따라서 참이 처음 시작되는 최소 시간의 경계를 이분 탐색함
- 이분 탐색 재사용 판단 규칙:
  1. 정답이 정수 형태의 최솟값 또는 최댓값인가?
  2. 정답 후보 범위가 커서 하나씩 확인하기 어려운가?
  3. 후보 `x` 하나가 가능한지 원래 문제보다 빠르게 판정할 수 있는가?
  4. 가능 여부가 한 방향으로만 바뀌는 단조성을 가지는가?
  5. 네 조건을 만족하면 `P(x): x로 조건을 만족할 수 있는가?`를 먼저 문장으로 작성하고 정답 범위를 이분 탐색함
- 대안 학습 상태: 완료 — 직접 배분 완전탐색의 병목과 시간에 대한 매개변수 탐색 전환을 학습함
- 코드 개선 포인트:
  - 가독성·안전성 개선: `while (left < right)`와 `return left`를 사용하면 `answer`와 `left == right` 특수 처리가 필요 없음
  - 안전성 개선: `left + (right - left) / 2`는 일반적인 이분 탐색에서 `left + right` 중간 합의 오버플로를 방지함. 이 문제의 현재 상한에서는 합도 `long` 범위 안이지만 재사용 가능한 습관임
  - 상수 비용 개선: `count >= n`이면 판정 결과가 이미 정해졌으므로 나머지 심사대를 계산하지 않고 중단할 수 있음. 빅오는 동일함
- 클린 코드 예시:

```java
public long solution(int n, int[] times) {
    long left = 0;
    long right = (long) Arrays.stream(times).min().getAsInt() * n;

    while (left < right) {
        long mid = left + (right - left) / 2;
        long processed = 0;

        for (int time : times) {
            processed += mid / time;
            if (processed >= n) {
                break;
            }
        }

        if (processed >= n) {
            right = mid;
        } else {
            left = mid + 1;
        }
    }

    return left;
}
```

- 풀이 후 새로 배운 점:
  - 배분 경우를 직접 만들기보다 후보 시간으로 처리 가능한 사람 수를 계산하면 배분은 자동으로 판정식에 흡수됨
  - `right = mid`는 가능한 `mid` 자체가 최소 정답일 수 있어 후보에서 제거하지 않는 갱신이며, `right = mid - 1`을 쓰려면 별도의 `answer` 저장 방식과 함께 사용해야 함
  - 현재 상한에서는 각 심사대 처리 인원이 최대 `n`, 전체 누적은 최대 `n × 100,000 = 10^14`이므로 `long count`가 안전함
- 다음 문제에 적용할 한 문장 규칙: **정답을 직접 구성하는 경우의 수가 너무 많다면, 정답 후보 하나의 가능 여부를 빠르게 판정할 수 있고 그 결과가 단조적인지 먼저 확인한다.**
- 복습에 포함할 학습 포인트: 위의 이분 탐색 판단 질문 네 가지를 코드 전에 다시 답하기, 배분 최적화에서 시간 판정으로 바꾸는 과정, `M`이 심사대 개수이고 후보 판정이 `O(M)`인 이유, `sum(T / time)`의 의미, 최소 가능 값을 찾는 경계 갱신, `long` 사용 위치와 조기 종료
- 오류 분류: 인식·설계·구현
- 잘한 점: 직접 배분의 경우의 수가 너무 크다는 병목을 확인했고, 힌트 후에는 `long` 범위와 최소 가능 시간의 이분 탐색 구조를 이해해 최종 통과함
- 개선할 점: 최적 배분을 직접 만들기 전에 `시간 T가 주어졌을 때 가능한가`라는 결정 문제를 먼저 만들어 보고, 이분 탐색의 두 구현 형태를 섞지 않도록 반복 조건과 경계 갱신을 한 세트로 선택해야 함
- 유형 인식 신호: 정답이 수치 최솟값·최댓값이고 후보 값의 가능 여부가 한 방향으로만 변하며, 각 후보를 제한 시간 안에 판정할 수 있음
- 다음에 적용할 규칙: 최소 가능 값을 찾는 `left < right` 형식에서는 `가능 → right = mid`, `불가능 → left = mid + 1`, 종료 후 `left`를 반환함
- 시간복잡도: `O(M log(minTime × n))` — 최대 약 60번의 이분 탐색마다 `M`개 심사대를 확인함
- 공간복잡도: `O(1)` — 입력 외에 경계와 누적 인원만 사용함
- 원본 코드 변경: 없음 — 개선 코드는 회고에만 기록함
