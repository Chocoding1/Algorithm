## 풀이 전 핵심 기록 - 사용자 작성

> 각 항목은 한두 문장이면 충분합니다. 완벽하게 쓰려 하지 말고 구현 전에 생각한 내용을 적습니다.

- 문제를 한 문장으로: 문자열 비교로 한 번호가 다른 번호의 첫번째 인덱스부터 한 번호의 길이만큼 다른 번호를 잘라서 비교하고 동일하면 false 후 리턴, 아니면 끝까지 비교해서 true 리턴
- 제한사항과 목표 시간복잡도: 데이터 개수는 1000000개, 즉 O(N^2)은 불가. O(NlogN), O(N)을 생각해볼 수 있겠음
- 가장 단순한 풀이와 병목: 배열의 첫 번째 원소를 기준으로 나머지 원소들 전부 비교, 그 다음 두번째 원소를 기준으로 나머지 원소들 비교하는 방식. / 이렇게 되면 O(N^2)이라 시간 초과될 듯
- 선택한 접근과 선택 이유: 배열 정렬 후, 0번 인덱스부터 순회하며 다음 번호와 일치하면 false 반환, 일치하지 않으면 다음 인덱스로 넘어가는 방식으로 시도. 이렇게 되면 O(N)의 시간복잡도를 가짐
- 풀이 흐름: 배열 정렬 후, 0번 인덱스부터 순회하며 다음 번호와 일치하면 false 반환, 일치하지 않으면 다음 인덱스로 넘어가는 방식으로 사용.
- 정답을 보장하는 이유와 핵심 엣지 케이스: 배열 정렬에 O(NlogN)의 시간을 쓰고, 배열 순회에 O(N)을 사용하므로 최종 시간복잡도가 O(NlogN)으로 약 2천만번 반복으로 시간 제한을 넘지 않을 것이라고 판단.
- 출제 의도 알고리즘 추측: 추천문에서 유형이 사전 공개되어 지표 집계 제외

## Codex 분석

- 복습 등급: B
- 등급 판정 근거: 최종 정답은 맞았지만 목표 30분을 6분 초과했고, 목표 시간의 50%가 지난 26분에 설계를 확정했다. 작은 힌트를 사용했으며 첫 제출에서 문자열 정렬을 길이순으로 오해해 런타임 오류가 발생했다.
- 목표 시간 달성: 아니오 (36분 / 30분)
- 첫 시도 성공: 아니오 (첫 통과 전 런타임 오류 1회)
- 공식 출제 의도 알고리즘: 해시 (프로그래머스 고득점 Kit 분류)
- Codex 추천 목표 알고리즘: 해시 집합에 전체 번호를 저장한 뒤 각 번호의 접두사를 조회
- 공식 의도 일치 여부: 유효한 대안
- Codex 목표 일치 여부: 유효한 대안
- 실제 풀이와 의도 알고리즘 비교: 실제 풀이는 문자열을 사전순 정렬해 접두사 관계의 두 번호가 인접한다는 성질을 이용한다. 해시 풀이는 각 번호의 진접두사가 전체 번호 집합에 있는지 조회한다. 두 방법 모두 제한을 충분히 만족한다.
- 풀이 전 사고와 실제 코드의 차이: 풀이 전에는 모든 쌍 비교와 길이별 그룹화의 병목을 정확히 찾았지만 이를 줄일 배열 순서를 떠올리지 못했다. 작은 힌트 후 사전순 정렬을 선택했으나 문자열 정렬이 길이순이라는 가정과 인접 비교의 정답성 근거는 구현 전에 검증하지 못했다.
- 의도 알고리즘 추가 학습 이유: 추천문에서 해시 유형이 미리 공개됐지만 실제로는 정렬 대안을 사용했으므로, 풀이 완료 시 해시 집합 풀이를 확인하고 D+3에는 정렬 풀이와 코드 없이 비교·회상한다.
- 풀이 직후 확인한 의도 알고리즘: 모든 전화번호를 `HashSet`에 저장한다. 각 번호마다 전체 번호 자체를 제외한 진접두사 `phone.substring(0, end)`를 만들고 집합에 존재하는지 조회해, 하나라도 있으면 `false`, 끝까지 없으면 `true`를 반환한다. 해시 조회를 평균 `O(1)`로 보더라도 Java의 부분 문자열 생성 비용까지 포함하면 최대 길이를 `L`이라 할 때 `O(N × L²)`, 공간은 저장된 문자열 기준 `O(N × L)`이다. `L`이 최대 20이라 제한을 충분히 만족한다.
- 대안 학습 상태: 완료 (풀이 직후 해시 접근 설명 완료, D+3 회상 예정)
- 코드 개선 포인트: 현재 `substring()`은 비교할 때마다 새 문자열을 만든다. `phone_book[i + 1].startsWith(phone_book[i])`를 사용하면 별도 부분 문자열과 명시적 길이 검사를 없앨 수 있다. 점근 복잡도는 동일하지만 임시 객체 생성, 가독성, 범위 오류 위험이 줄어든다.
- 개선 예시: `if (phone_book[i + 1].startsWith(phone_book[i])) return false;`
- 풀이 후 새로 배운 점: ① 사전순 정렬은 길이순이 아니지만 접두사 관계의 문자열을 같은 구간에 모아 인접 비교를 가능하게 한다. ② 해시 집합에 전체 번호를 저장하고 각 진접두사를 조회하는 의도 풀이도 가능하다. ③ `startsWith()`는 `substring()` 생성과 길이 범위 오류를 피하면서 접두사 비교 의도를 직접 표현한다.
- 다음 문제에 적용할 한 문장 규칙: 문자열의 접두사·중복 관계를 모든 쌍에서 찾고 있다면 해시 존재 조회 또는 사전순 정렬 후 인접 비교가 가능한지 확인한다.
- 복습에 포함할 학습 포인트: D+3에 “왜 사전순 정렬 후 인접 비교로 충분한가?”, “해시 풀이는 무엇을 저장하고 무엇을 조회하는가?”, “`startsWith()`가 없애는 작업은 무엇인가?”를 코드 없이 답한다.
- 오류 분류: 인식·구현·시간 관리
- 잘한 점: 모든 쌍 비교와 길이별 그룹화가 최악의 경우 비교량을 충분히 줄이지 못한다는 점을 스스로 판단했다. 힌트 후에는 사전순 정렬과 인접 비교로 풀이를 완성했고, 길이가 반대인 인접 쌍에서 발생한 예외도 바로 보완했다.
- 개선할 점: 시간복잡도뿐 아니라 “접두사인 두 문자열은 사전순 정렬 후 그 사이에 다른 문자열이 끼더라도 같은 접두사 구간 안에서 인접 쌍이 반드시 생긴다”는 정확성 근거를 구현 전에 확인한다. `substring` 사용 시 범위를 먼저 검증하거나 `startsWith` 사용을 고려한다.
- 유형 인식 신호: 큰 입력에서 문자열의 접두사 포함 여부를 반복 확인해야 한다. 전체 쌍 비교 대신 빠른 존재 조회 또는 접두사 후보가 가까워지는 정렬을 고려한다.
- 다음에 적용할 규칙: 접두사 문제에서는 해시로 진접두사를 조회하는 방법과 사전순 정렬 후 인접 비교를 후보로 놓고 복잡도와 구현 위험을 비교한다. 문자열 정렬은 길이순이 아니라 사전순이라는 점을 먼저 확인한다.
- 시간복잡도: `O(N log N × L)` — 문자열 정렬 비교에 최대 `L`이 들고, 인접 쌍 검사는 `O(N × L)`이다.
- 공간복잡도: `O(N)` — Java 객체 배열 정렬의 보조 공간 기준이며, 접두사 비교 중 임시 문자열 공간이 추가될 수 있다.
- 정답 검증: 프로그래머스 공개 예제와 단일 번호, 앞·뒤 순서가 바뀐 접두사, 길이가 더 긴 문자열이 앞서는 인접 쌍 등 추가 경계 사례를 Java 21에서 통과했다.
