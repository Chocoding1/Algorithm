- 복습 등급: B
- 등급 판정 근거: 이전 코드·해설을 다시 보지 않고 10분 만에 설계를 확정해 목표 35분 안인 30분에 재도전을 성공했고 공식 제출도 첫 번에 통과했다. 다만 구현 중 빈 큐에서 `peek()`를 호출해 로컬 오류가 발생했고, 정답 근거에는 출차 시각을 저장한다는 설명은 있으나 만료 트럭을 지연 제거해도 진입 가능 시각을 놓치지 않는 이유가 충분히 드러나지 않아 B등급이다.
- 목표 시간 달성: 예 (30분 / 35분)
- 첫 시도 성공: 대상 아님 (동일 문제 재도전)
- 공식 출제 의도 알고리즘: 공식 의도 명시 없음
- Codex 추천 목표 알고리즘: 큐에 `(트럭 무게, 출차 시각)`을 저장하고 필요한 출차 이벤트 시각으로 이동하는 `O(N)` 시뮬레이션
- 공식 의도 일치 여부: 공식 의도 명시 없음
- Codex 목표 일치 여부: 일치 (정답 코드 없이 독립 재현)
- 실제 풀이와 의도 알고리즘 비교: 큐에 트럭의 무게와 출차 시각을 넣고, 다음 트럭이 현재 잔여 중량으로 진입할 수 없을 때 앞 트럭부터 제거하며 시간을 그 출차 시각으로 이동한다. 이는 매초 다리 전체를 갱신하지 않고 상태가 변하는 이벤트만 처리하는 목표 풀이와 일치한다.
- 풀이 전 사고와 실제 코드의 차이: 풀이 전 정한 `(무게, 출차 시각)` 큐 설계를 그대로 구현했다. 다만 메모에서는 매초 출차 트럭을 제거한다고 적었지만 실제 코드는 중량이 부족해질 때까지 만료 트럭을 큐에 남겨 두는 지연 제거 방식을 사용했다.
- 의도 알고리즘 추가 학습 이유: 핵심 알고리즘은 독립적으로 재현했으므로 새로운 알고리즘 학습은 필요하지 않다. 대신 지연 제거 상태의 의미를 정확히 설명하거나, 실제 다리 상태와 변수가 항상 일치하도록 만료 트럭을 즉시 제거하면 코드의 검증이 쉬워진다.
- 풀이 직후 확인한 의도 알고리즘: 다음 트럭의 진입 후보 시각을 1초 증가시키고 현재 시각까지 나간 트럭을 제거한다. 중량이 부족하면 큐 맨 앞의 출차 시각으로 이동하고 그 시각까지 나간 트럭을 제거한 뒤, 새 트럭과 `현재 시각 + 다리 길이`를 큐에 넣는다.
- 대안 학습 상태: 완료 (2026-10-01 정답 코드 없이 독립 재현)
- 코드 개선 포인트: **가독성·상태 안전성 개선** — 현재 코드도 `O(N)`으로 정확하지만, 만료된 트럭을 중량이 필요할 때만 제거해서 `remainWeight`가 실제 다리의 즉시 사용 가능 중량보다 작을 수 있다. 진입 판단 전에 만료 트럭을 제거하고 `currentWeight`를 실제 다리 위 중량으로 유지하면 불변식이 명확해진다. `ArrayDeque` 구현체는 `Queue` 인터페이스 타입으로 선언하고, 마지막 출차 시각은 마지막 진입 시각에 `bridge_length`를 더해 반환할 수 있다. 점근 복잡도는 변하지 않는다.
- 클린 코드 예시:

```java
public int solution(int bridge_length, int weight, int[] truck_weights) {
    Queue<int[]> bridge = new ArrayDeque<>();
    int time = 0;
    int currentWeight = 0;

    for (int truckWeight : truck_weights) {
        time++;

        while (!bridge.isEmpty()
                && (bridge.peek()[1] <= time || currentWeight + truckWeight > weight)) {
            int[] exitedTruck = bridge.poll();
            time = Math.max(time, exitedTruck[1]);
            currentWeight -= exitedTruck[0];
        }

        bridge.offer(new int[]{truckWeight, time + bridge_length});
        currentWeight += truckWeight;
    }

    return time + bridge_length;
}
```

- 풀이 후 새로 배운 점: ① C등급 문제의 핵심 상태인 `무게·출차 시각`을 정답 코드 없이 다시 만들 수 있었다. ② 지연 제거도 정확하지만 변수와 실제 상태가 어긋나므로 정확성 설명이 어려워질 수 있다. ③ 큐는 `Queue<int[]> bridge = new ArrayDeque<>()`처럼 역할을 인터페이스로, 저장 방식을 구현체로 선언할 수 있다. ④ `offer()`·`peek()`·`poll()` 조합을 사용할 때 `peek()`와 `poll()` 전에 빈 큐 여부를 확인한다.
- 다음 문제에 적용할 한 문장 규칙: 이벤트 큐에서는 큐 원소, 현재 시간과 누적 상태가 현실의 어떤 상태를 나타내는지 반복문 시작과 끝마다 한 문장으로 정의한다.
- 복습에 포함할 학습 포인트: 큐의 맨 앞이 다음 출차 이벤트인 이유, 중량 부족 시 시간 점프 후 같은 시각의 트럭을 함께 제거하는 이유, 각 트럭이 한 번 들어가고 나와 `O(N)`인 이유, 빈 큐 접근 방지.
- 오류 분류: 구현·정확성 설명 보완
- 잘한 점: 이전 코드와 해설을 확인하지 않고 10분 만에 핵심 상태를 다시 정의했으며, 목표 시간 안에 첫 공식 제출로 통과했다. 첫 시도에서 어려웠던 시간 이벤트 설계를 독립적으로 재현했다.
- 개선할 점: `peek()`·`poll()` 사용 전 빈 큐 여부를 조건의 가장 앞에서 확인한다. 정답 근거에는 마지막 출차 시각뿐 아니라 큐의 순서, 진입 가능 판단과 시간 점프가 모든 경우를 빠짐없이 처리하는 이유를 적는다.
- 유형 인식 신호: 객체가 들어온 순서대로 나감, 다음 행동 가능 시점이 맨 앞 객체의 종료 시각에 의해 결정됨, 매초 전체 상태 갱신을 이벤트 이동으로 줄일 수 있음.
- 다음에 적용할 규칙: 시간이 있는 순서 시뮬레이션에서는 객체마다 다음 상태 변화 시각을 저장하고 큐의 맨 앞 이벤트로 시간을 이동할 수 있는지 확인한다.
- 시간복잡도: `O(N)` — 각 트럭이 큐에 한 번 들어가고 최대 한 번 제거된다.
- 공간복잡도: `O(N)` — 최악의 경우 다리 위 또는 지연 제거 전의 트럭 정보를 큐에 저장한다.
- 정답 검증: Java 21에서 컴파일했고 공개 예제 3개가 `8`, `101`, `110`으로 일치했다. 추가로 다리 길이 1~5, 중량 1~10, 트럭 수 1~5의 1,248,115개 입력을 1초 단위 단순 시뮬레이션과 비교해 결과가 모두 일치했다.
