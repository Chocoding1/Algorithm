## 오늘의 평가

- `다리를 지나는 트럭`은 최초 C등급 이후 `(무게, 출차 시각)` 큐 설계를 10분 만에 독립적으로 재현했다. 목표 시간 안에 첫 제출로 통과해 시간·이벤트 시뮬레이션의 핵심 상태는 회복됐다.
- 재도전 코드의 지연 제거 방식은 정확하지만 `remainWeight`가 실제 순간의 잔여 중량보다 작을 수 있어 검증이 어렵다. 진입 전 만료 트럭을 제거하고 실제 다리 위 중량을 유지하는 코드로 같은 `O(N)` 안에서 상태를 더 명확하게 표현하는 방법을 학습했다.
- `올바른 괄호`는 2분 30초 만에 스택 설계를 확정하고 10분에 통과했다. 괄호 종류가 하나뿐이면 스택 대신 미결 여는 괄호 개수만 유지해 공간을 `O(1)`로 줄일 수 있다.
- 두 문제 모두 복잡도 판단과 구현 속도는 좋았다. 다음 보완점은 복잡도와 정답성 근거를 분리하고, `peek()`·`poll()` 전에 빈 큐를 확인하며, 변수가 실제 상태와 항상 일치하는지 설명하는 것이다.

## 풀이 후 새로 배운 점

### 다리를 지나는 트럭

- 시간 시뮬레이션에서 객체의 다음 상태 변화 시각을 큐에 저장하면 매초 전체 상태를 갱신하지 않아도 된다.
- 지연 제거 방식도 정답이지만, 만료 이벤트를 먼저 제거해 누적 중량을 실제 상태와 일치시키면 불변식과 코드 검증이 쉬워진다.
- `Queue<int[]> bridge = new ArrayDeque<>()`는 필요한 역할을 인터페이스로, 실제 저장 방식을 구현체로 표현한다.
- `peek()`와 `poll()`은 빈 큐에서 `null`을 반환하므로, 배열 원소에 접근하기 전 `isEmpty()`를 확인한다.

### 올바른 괄호

- 스택에 저장되는 값이 모두 같고 개수만 필요하면 정수 카운터로 상태를 줄일 수 있다.
- 모든 접두사에서 미결 여는 괄호 수가 음수가 되면 안 되고, 전체 처리 후 0이어야 한다.
- 복잡도는 제한 시간 안에 실행되는 이유이고, 불변식은 정답이 보장되는 이유다.
