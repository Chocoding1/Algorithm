## 1. 학습자 정보와 목표

- 준비 분야: 국내 백엔드 개발자 채용 코딩테스트
- 사용 언어: Java
- 과거 수준: 백준 Gold 1
- 현재 체감 수준: 긴 공백 이후 프로그래머스 Lv.2 초반
- 1차 목표 시점: 2026년 11월 말 일반적인 국내 백엔드 기업 코딩테스트 안정 합격권
- 학습 빈도: 월요일~금요일과 일요일, 주 6일
- 평일 학습량: Java 알고리즘 정확히 2문제 + MySQL SQL 정확히 2문제
- 일요일 학습량: Java 알고리즘 3문제 120분 실전 세트 + MySQL SQL 주간 혼합 정확히 2문제
- 토요일: 고정 일정으로 휴식
- 핵심 목표: 어려운 프로그래머스 Lv.2를 안정적으로 해결하고 핵심 유형의 Lv.3 입문 문제까지 다루며, 유형이 공개되지 않은 120분 3문제 실전에서 최소 2문제를 완전 해결할 수 있는 수준으로 끌어올린다.

## 2. 역할 분담

### 문제 추천 실행 방식

- 특정 시각에 자동으로 문제를 추천하거나 알림을 보내지 않는다.
- 사용자가 이 Codex 대화에서 `오늘 문제 추천해`처럼 명시적으로 요청한 경우에만 그날의 문제를 추천한다.
- 추천 요청을 받으면 월요일~금요일에는 알고리즘 2문제, SQL 2문제와 필요한 짧은 복습을 제공하고, 일요일에는 유형을 공개하지 않은 알고리즘 3문제 120분 실전 세트와 SQL 주간 혼합 2문제를 제공한다. 토요일은 고정 휴식일이다.
- 문제 페이지 접근 가능 여부와 직접 링크를 확인하고, 저장소의 최신 코드·회고·지표·복습 일정을 읽어 문제와 난이도를 조절한다.
- 사용자가 풀이 질문, 복습 또는 완료 처리를 요청했을 때는 별도의 명시적 추천 요청이 없는 한 다음 문제를 선제적으로 추천하지 않는다.

## 3. 문제 추천 원칙

- 월요일~금요일은 알고리즘 2문제, 일요일은 알고리즘 3문제 실전 세트로 유지하고 SQL 2문제를 별도로 추가한다.
- 일반적으로 1번은 복습 또는 핵심 유형, 2번은 같은 주제의 응용이나 한 단계 어려운 문제로 구성한다.
- 실패했거나 해설을 본 문제는 2~3일 뒤 2문제 중 하나로 재편성한다.
- 백준은 현재 추천 대상에서 제외한다.
- 플랫폼 우선순위는 프로그래머스, LeetCode, 코드트리, SW Expert Academy 순이다.
- 신규 문제는 중복 추천하지 않고, 명시적인 재도전일 때만 같은 문제를 다시 제시한다.
- 정답, 핵심 풀이법과 사용할 알고리즘을 문제 추천 단계에서 직접 노출하지 않는다.
- 신규 알고리즘 문제는 핵심 유형·자료구조·알고리즘명을 공개하지 않는다. 추천 이유에서도 학습할 유형이나 이전 문제와의 알고리즘 연결을 밝히지 않는다.
- 풀이 전 질문은 `제한에서 허용되는 복잡도`, `단순 풀이의 병목`, `정답 검증과 엣지 케이스`처럼 어느 알고리즘에도 적용되는 중립 질문만 사용한다. `큐에 무엇을 저장할까`, `방문 배열이 필요한가`처럼 특정 풀이를 유도하는 질문은 금지한다.
- D+7 신규 변형은 풀이 전에는 연결된 원본 문제를 밝히지 않고, 완료 후 전이 성공을 분석할 때 연결한다. 동일 문제 재도전은 예외로 한다.
- 힌트 요청 시 정답 코드가 아닌 다음 사고를 유도하는 최소 힌트부터 제공한다.

각 추천 문제에는 다음을 포함한다.

- 플랫폼과 난이도
- 알고리즘과 자료구조를 노출하지 않는 중립적인 추천 이유
- 목표 풀이 시간
- 풀이 전 중립 확인 질문 2~3개

핵심 유형, 공식 출제 의도와 Codex 목표 알고리즘은 풀이 완료 후 기록한다. 풀이 전에 이를 알려주면 사실상 힌트가 되는 경우가 있으므로 보이는 문서에 미리 채우지 않는다.

### SQL 추천 원칙

- 첫 4주는 프로그래머스 MySQL 문제를 사용하고 `SQL_PLAN.md`의 순서를 따른다.
- SQL은 문법을 처음 배우는 구간이므로 오늘 연습할 범주는 공개하되 정답 쿼리 구조는 공개하지 않는다.
- 1주차는 Lv.1과 15~20분, 2주차는 Lv.1~2와 20~25분, 3주차는 Lv.2와 25~30분, 4주차는 Lv.2 중심 25~35분을 기본값으로 한다.
- SQL B등급 짧은 복습은 5분을 넘기지 않고, C등급 동일 문제 재도전은 그날 SQL 2문제 중 한 문제를 대체한다. 다른 한 문제에서는 신규 진도를 이어간다.
- 알고리즘과 SQL 난이도는 서로 독립적으로 조절한다.

## 4. 2026년 11월 말 기업 코딩테스트 대비 압축 진도

기존 12주 유형 지도는 학습 범위 참고용으로 유지하되, 2026년 11월 2일부터 30일까지는 일반적인 국내 백엔드 기업 코딩테스트의 안정 합격권을 목표로 아래 순서로 운영한다. 최상위 플랫폼 기업의 고난도 시험까지 무난한 합격을 보장하는 계획은 아니며, 어려운 Lv.2 안정화·핵심 Lv.3 입문·유형 비공개 실전에서의 점수 확보를 우선한다.

### 2026-11-23~12-01 우아한형제들 신입 코딩테스트 최종 운영 — 최우선

아래 계획을 기존 11월 주차별 계획보다 우선한다. 11월 25일 우아한형제들 신입 채용설명회에서 사용자가 확인한 12월 1일 시험은 **180분에 프로그래밍 3문제와 SQL 1문제, 총 100점**이며 문항별 부분 점수가 가능하다. 설명회에서는 대략 60%를 쉽게 풀 수 있는 난이도로 설명했고 마지막 한 문제는 더 고민이 필요하다고 했다. 60%는 난이도 안내로 기록한다. 문항별 배점과 합격선은 미확인이다. 1차 면접관은 제출 코드를 읽고 스타일과 고민의 흔적을 본다. 테스트 코드는 선택이며 시간이 남을 때 작성한다. 응시 공지에 따라 시험과 모의고사에서는 웹 편집기를 사용한다.

11월 25일에 알고리즘은 3문제 최종 통과·1문제 첫 제출 통과, SQL은 1문제 최종 통과·1문제 미제출이었다. 남은 기간에는 초반에 풀 수 있는 문제의 점수를 확보하고, 작은 경계 입력 검증과 읽기 쉬운 코드로 제출을 안정화한다.

#### 문제 선정 우선순위

1. 구현·시뮬레이션·상태 변화·문자열·해시
2. 기본 DP와 그래프 관계·도달성
3. 그리디·정렬·투 포인터
4. 다익스트라·기본 최단거리와 매개변수 탐색 유지
5. 스택·큐·힙과 Union-Find 유지

위상정렬은 실전 결과에서 직접적인 결손이 드러나지 않는 한 시험 전 신규 학습에서 제외한다. 기존 복습 대기열도 날짜순으로 소진하지 않고 위 우선순위나 직전 실패 원인에 연결되는 항목만 당일 문제에 흡수한다. 11월 23일에 실제로 풀었지만 11월 19일 폴더에 기록한 `프렌즈4블록`과 해당 SQL 문제는 11월 23일 신규 문제 수에 포함하지 않는다.

#### SQL 난이도와 유형 운영

- SQL 2문제는 원칙적으로 `기본·취약점 보정 1문제 + 프로그래머스 Lv.3~4 복합 1문제`로 구성한다. 현재 첫 제출 성공률이 낮으므로 두 문제를 모두 고난도로 편성하지 않는다.
- 복합 문제는 `다중 JOIN + GROUP BY/HAVING`, 1:N JOIN 중복 제어, 상관 서브쿼리와 `EXISTS/NOT EXISTS`, `CASE` 조건부 출력·집계, 날짜 계산과 기간 조건의 조합을 우선한다.
- 시험 전 SQL 시간은 이미 배운 JOIN·집계·날짜 경계·출력 검증에 집중한다. 기초 윈도 함수 신규 학습은 시험 후에 검토한다.
- 재귀 CTE, 복잡한 윈도 프레임, 고급 통계 함수, 실행 계획·성능 튜닝과 MySQL 특수 문법은 시험 전 신규 범위에서 제외한다.
- 11월 26일에는 날짜 범위와 조건부 집계를 보정한다. 27일에는 처음 보는 SQL 하나를 시간 안에 풀고 대여 가능 여부 재도전을 따로 한다. 28일에는 유형 비공개 신규 혼합 SQL 한 문제를 180분 타이머에 포함한다. 29일 오후에는 28일에 놓친 조건을 새 문제 한 개에서 20~25분 동안 다시 검증한다. 28일에 첫 제출을 통과했다면 새로운 혼합 문제에서 첫 제출 정확성을 확인한다. 30일에는 출력과 날짜 경계를 짧게 확인한다.

#### 실전과 제출 규칙

- 11월 28일과 실제 시험 시간 배분 초안은 **0~10분 전체 4문제 읽기, 10~115분 빠르게 완성할 프로그래밍 2문제와 SQL 1문제, 115~160분 변별력 문항, 160~180분 검증·코드 점검**이다. SQL과 프로그래밍의 순서는 읽고 판단한 체감 난이도에 따라 바꾼다. 남은 시간과 이미 확보한 제출을 보고 구간을 조정한다.
- 한 문제에서 25분까지 실행 가능한 설계가 없으면 다음 문제로 전환하고, 한 문제에 50분 이상 연속 고착하지 않는다.
- 변별력 문항의 전체 풀이가 막히면 문제에서 공개한 제한이나 테스트 그룹을 근거로, 그 범위에서 정확하게 동작하는 풀이를 검증해 제출한다. 제출·재제출 방식은 응시 화면 규칙을 따른다.
- 마지막 20분은 예제·최소/최대 입력·인덱스·자료형·출력 형식 검증과 코드 점검에 남긴다. 변수는 의미가 드러나는 이름을 쓰고, 주석은 근거가 필요한 선택이나 유지 조건에 짧게 단다. 임시 출력과 확인용 코드를 정리한다. 테스트 코드는 최종 제출 확인 후 남은 시간에 정해진 형식으로 작성한다.
- 유형 비공개 실전에서는 힌트를 사용하지 않는다. 일반 훈련은 목표 시간 60%에 작은 힌트, 추가 10분 뒤 핵심 힌트, 총 45~50분에 학습용 해설로 전환하는 기존 규칙을 유지한다.
- SQL 제출 전 `출력 컬럼 수·순서 → 계산 컬럼 별칭 → 작은따옴표/백틱 → FROM/JOIN 후 한 행의 의미 → 중복·NULL → 반열린 날짜 범위 → 정렬 방향·동점 기준`을 확인한다.

Lv.1 신규 문제는 원칙적으로 편성하지 않는다. C등급 재도전, 명확한 기초 결손 보완 또는 10분 이내 워밍업이 필요한 경우에만 예외로 사용한다.

매주 일요일에는 유형을 공개하지 않은 3문제 120분 실전 세트를 진행한다. 실전 세트는 처음 보는 신규 문제와 연결 원본을 미리 공개하지 않은 D+7 변형만 사용하고, 기존 코드를 알고 있는 동일 문제 재도전은 제외한다. 목표는 최소 2문제 완전 해결이며, 세트가 끝난 뒤 문제 선택 순서, 첫 10분 판단, 시간 배분, 포기·전환 시점을 날짜 폴더의 `README.md`에 한 번만 짧게 회고한다. 문제별 `review.md`에는 이를 반복하지 않으며 전환이 없었다면 `전환 없음`만 기록한다. 토요일은 고정 휴식일이다.

SQL은 알고리즘 압축 진도와 별도로 첫 4주 입문 과정을 유지한다. 세부 계획은 `SQL_PLAN.md`에 기록하며 매 학습일 2문제, 일요일에는 해당 주 SQL 문법을 섞은 2문제를 푼다. 11월에는 알고리즘 실전 안정화를 우선하므로 SQL 두 문제 합계는 30~40분을 기준으로 하고, 두 번째 문제에서 20분 이상 막히면 다음 학습일의 재도전 슬롯으로 넘긴다.

## 5. 문제 접근 순서

문제를 풀 때 다음 순서를 따른다.

1. 문제를 내 말로 한 문장으로 재정의한다.
2. 입력 크기, 값 범위와 제한사항을 확인한다.
3. 허용 가능한 목표 시간복잡도를 추정한다.
4. 작은 예제를 손으로 따라간다.
5. 가장 단순한 풀이와 그 시간복잡도를 적는다.
6. 단순 풀이의 병목과 반복 계산을 찾는다.
7. 알고리즘과 자료구조 후보를 근거와 함께 비교한다.
8. 선택한 알고리즘에 맞게 입력을 어떤 순서로 처리해 답을 만드는지 풀이 흐름을 정리한다. DP의 상태·점화식, 그래프의 방문·이동, 그리디의 선택 기준처럼 필요한 세부 요소는 유형에 맞게 사용한다.
9. 정답을 보장하는 이유를 확인한다.
10. 엣지 케이스와 직접 만든 반례를 점검한다.
11. 의사코드를 작성한 뒤 Java로 구현한다.

최소한 문제와 제한·목표 복잡도, 단순 풀이의 병목, 확정한 설계와 처리 흐름, 정답 근거와 엣지 케이스는 구현 전에 확인한다.

### 초기 경량 기록 방식

- 처음부터 과도하게 문서화해 학습 지속성을 해치지 않도록, 사용자는 `review.md`에 각 항목을 한두 문장으로만 작성한다.
- 2026-11-02부터 새 문제의 풀이 전 기록은 목표 시간 비율에 맞춘 질문형 양식을 사용한다. `0~20% 문제·제한`, `20~40% 단순 풀이·병목`, `40~60% 설계 확정`, `60% 힌트 판단`, `60~85% 구현`, `85~100% 검증` 순서로 배치하고, 각 구간 제목에는 목표 시간을 환산한 실제 분 범위를 함께 적는다. 특히 힌트 판단 시점은 `60% (N분)`으로 명시하며, 각 질문 바로 아래에 한두 문장으로 답한다.
- 질문형 양식에는 체크박스와 별도의 완료 문장을 넣지 않는다. 구현 중 주의사항이 없으면 해당 답은 비워도 되고, 출제 의도 추측은 선택 항목으로 유지한다. 이 양식은 기존 네 가지 핵심 기록을 시간 순서로 재구성한 것이므로 같은 내용을 별도 항목에 중복 작성하지 않는다.
- 질문은 실제 매개변수명과 문제의 요구사항에 맞춰 작성한다. 배열 원소·문자열 한 줄·행·정점 등 데이터 단위의 의미가 문제 이해에 필요할 때만 구체적으로 묻고, 단순 숫자처럼 의미가 자명한 값에는 억지로 의미를 부여해 질문하지 않는다. 한 문장에는 한 가지 판단만 요구하고, 별도 해석 없이 무엇을 답해야 하는지 바로 알 수 있는 쉬운 표현을 사용한다. `입력 한 개`처럼 범위가 불분명한 공통 문구, 아직 선택하지 않은 상태·자료구조·처리 방식을 전제하는 문구, 특정 알고리즘이나 자료구조를 유도하는 문구는 사용하지 않는다. 상태 변화가 복잡한 문제라도 앞 질문만으로 부족할 때만 문제별 추가 질문을 1~2개 넣으며, `객체·상태·사건·처리 순서·종료 조건은?`처럼 여러 개념을 한꺼번에 나열하거나 기존 질문과 중복하지 않는다.
- 검증 구간의 질문은 최소 입력, 반복문 실행 횟수 0·1·여러 번·입력 끝까지, 조건식의 직전·같음·직후, 사건이 발생하지 않음·한 번·연속 발생, 첫·마지막·정답 없음, 중복·동률, 남은 불완전 구간, 숫자 자릿수 변화, 자료형·최대 복잡도에서 해당 문제에 실제로 위험한 2~3개만 선택한다. 반복 종료 후 확정되지 않은 상태가 남는지와 `continue`·`break`를 포함한 모든 경로에서 인덱스가 전진하는지도 실제 변수와 상황으로 묻는다. 특정 풀이를 암시할 수 있는 검증 질문은 풀이 전에는 넣지 않고, 문제 조건만으로 확인 가능한 경계에 한정한다.
- 2026-11-01까지 생성된 기존 회고 양식과 사용자 기록은 수정하지 않는다.
- 출제 의도 알고리즘 추측은 선택 항목이며, 기록하려면 Codex 피드백 전에 작성한다.
- 풀이 후에는 실제 풀이 시간, 제외 시간, 결과, 제출 결과, 설계 확정 시간, 구현 실수와 막힌 지점·배운 점만 기록한다. 힌트 수준은 사용자가 적지 않고 Codex가 실제 대화와 확인한 외부 자료를 기준으로 판정한다.
- 풀이 후 결과의 각 줄은 `- 실제 풀이 시간:  (예: \`15분\`)`처럼 콜론과 오른쪽 괄호 예시 사이에 실제 값을 바로 적는 형식으로 만든다. 사용자는 예시를 지우지 않고 왼쪽 빈칸에 답하며, Java와 SQL 신규 문제 모두 실제·제외 시간, 결과, 제출 결과, 오류와 막힌 지점에 짧은 예시를 제공한다. 완료된 과거 회고는 소급 수정하지 않는다.
- 상세 복잡도 분석, 풀이 전 메모와 실제 코드의 차이, 공식·추천 의도 비교, 코드 개선, 풀이 후 새로 배운 점, 오류 분류, 등급, 복습 일정과 대시보드 지표는 Codex가 코드와 사용자 기록을 바탕으로 작성한다.
- 템플릿의 예시 답변은 작성 형식을 익히기 위한 참고이며 새 문제의 답으로 복사하지 않는다. 사용자가 익숙해지면 예시를 생략할 수 있다.

### 목표 시간 배분

- 1단계 문제 이해·제한 확인: 목표 시간의 20%
- 2단계 단순 풀이·병목 찾기: 목표 시간의 20%
- 3단계 접근 선택·풀이 흐름·정확성 확인: 목표 시간의 20%
- 4단계 Java 구현: 목표 시간의 25%
- 5단계 예제·엣지 케이스 검증 및 제출: 목표 시간의 15%
- Codex는 문제 파일을 만들 때 비율을 분 단위로 반올림하고 합계가 목표 시간과 같도록 마지막 단계를 조정해 `review.md`의 표와 각 시간대별 구간 제목에 채운다. 힌트 판단 시점에는 목표 시간의 60%에 해당하는 정확한 분을 별도로 표시한다.
- 목표 시간의 60% 시점까지 접근을 확정하고 구현을 시작하며, 85% 시점에는 검증과 제출 단계로 넘어간다.

## 6. 반복 복습 규칙

정답 여부만으로 복습 강도를 정하지 않고 풀이의 안정성을 A·B·C로 분류한다.

### A등급: 안정적으로 성공

- 조건: 목표 시간 안에 성공, 힌트·해설 없음, 코드와 풀이 흐름에서 알고리즘 선택 및 적용이 타당하고 중대한 구현 실수나 반복적인 오답 제출이 없음. 사용자의 한두 문장 회고에 엄밀한 정답성 증명이 빠졌더라도 코드와 설계에서 이해가 확인되면 A로 판정한다.
- D+1: 생략
- D+3: 핵심 신호·복잡도·엣지 케이스와 풀이 직후 새로 배운 핵심 항목이 있으면 함께 2~3분 회상
- D+7: 핵심 유형이거나 최근 취약 유형일 때만 새로운 변형 문제 풀이
- 동일 문제 재도전: 하지 않음

### B등급: 성공했지만 불안정

- 조건: 성공했지만 목표 시간 초과, 접근을 오래 헤맴, 의미 있는 구현 실수나 오답 제출, 작은 힌트 확인, 또는 코드와 설명에서 실제 이해 불안정·모순·우연한 정답의 증거가 확인된 항목 중 하나 이상에 해당함. 회고가 짧거나 세부 증명이 생략된 것만으로는 B로 낮추지 않는다.
- D+1: 사용한 알고리즘에 맞는 핵심 구조·풀이 흐름·정답 조건 설명
- D+3: 핵심 신호·알고리즘·복잡도·엣지 케이스와 풀이 직후 새로 배운 의도 풀이·최적화·API·정확성 근거 회상
- D+7: 같은 유형의 새로운 변형 문제 풀이
- 동일 문제 재도전: 중대한 구현 실수가 있었을 때 추가 가능

### C등급: 실패 또는 해설 확인

- 조건: 실패·부분 성공, 핵심 힌트나 해설 확인, 정답 코드 참고, 또는 유형을 알았더라도 상태나 설계를 완성하지 못한 항목 중 하나 이상에 해당함
- 2~3일 뒤: 동일 문제를 정답 코드 없이 처음부터 재도전
- 재도전 후 D+7: 같은 유형의 새로운 변형 문제 풀이
- 같은 실패가 반복되면 더 쉬운 문제로 유형을 다시 학습

### 공통 운영 규칙

- 동일 문제 재도전과 D+7 변형은 해당 학습일의 알고리즘 문제 수 안에 포함한다. 다만 동일 문제 재도전은 평일에만 주당 최대 2개를 편성하고, 일요일 120분 실전에는 처음 보는 D+7 변형과 신규 문제만 사용한다.
- 문제 2개 외의 짧은 회상 복습은 하루 최대 2개, 총 5~10분으로 제한한다.
- 우선순위: C등급 재도전 → B·C등급 D+7 변형 → B등급 D+3 → B등급 D+1 → A등급 D+3
- 맞힌 문제를 모두 동일 문제로 다시 풀게 하지 않는다. A등급은 동일 문제를 재도전하지 않고 짧은 회상과 필요한 변형 문제로만 복습한다.
- 등급 판단에 필요한 정보가 부족하거나 모호하면 임의로 판정하지 않는다. 누락된 질문을 한 번에 모아 사용자에게 확인한 뒤 등급을 확정한다.

### 객관적 판정 기준

- 실제 풀이 시간은 문제를 처음 읽은 시점부터 제출 성공 또는 풀이 종료까지의 경과 시간에서 1분 이상의 휴식, IDE·환경 설정과 다른 용무 시간을 뺀 값이다. 제외 시간이 있으면 분 단위로 별도 기록한다.
- 목표 시간 달성은 성공한 문제의 실제 풀이 시간이 목표 시간 이하일 때만 인정한다. 목표 시간을 넘긴 성공은 A등급이 될 수 없으며, C등급 사유가 없으면 B등급으로 판정한다.
- 큰 시간 초과는 초과분이 `목표 시간의 25%`와 `10분` 중 더 큰 값 이상인 경우다. 큰 시간 초과에는 시간 관리 오류를 기록한다. 그보다 작은 초과도 B등급이지만 시간 관리 오류는 다른 증거와 함께 판단한다.
- 첫 시도 성공은 신규 문제의 첫 공식 제출이 채점 통과한 경우다. 제출하지 못했거나 첫 공식 제출이 오답·시간 초과·런타임 오류·컴파일 오류이면 첫 시도 성공이 아니다.
- 오답 제출 횟수는 첫 통과 전 공식 제출에서 오답·시간 초과·런타임 오류·컴파일 오류가 난 횟수다. 로컬 실행 실패는 오답 제출 수에 넣지 않고 구현 실수에 기록한다.
- 구현 실수는 로컬 또는 제출 과정에서 확인된 인덱스·조건·자료형·API·초기화·엣지 케이스 오류다. 핵심 흐름이나 자료구조를 다시 작성했거나 오답·예외를 유발했다면 중대한 구현 실수로 기록한다. 단순 타이핑 실수를 실행 전에 바로 고친 경우는 제외한다.
- 접근을 오래 헤맨 경우는 구현 가능한 설계를 잡기 전에 목표 시간의 50% 이상을 사용했거나, 근거 없이 완성된 접근을 두 번 이상 폐기한 경우다.
- 힌트 수준은 `없음 / 작은 힌트 / 핵심 힌트 / 해설 / 정답 코드`로 기록하며 Codex가 실제 대화 기록과 사용자가 확인한 외부 자료를 근거로 판정한다. 사용자는 힌트 수준을 직접 작성하지 않는다. 알고리즘·상태·핵심 식을 노출하지 않는 일반 사고 유도는 작은 힌트로서 B등급 사유다. 진행 규칙·자료구조·상태·핵심 식·종료 조건을 직접 알려주면 핵심 힌트로 보고 C등급으로 판정한다. 전체 풀이 구조를 단계별로 설명하면 해설, 완성 코드를 제공하거나 확인하면 정답 코드로 기록한다. 문제 재진술이나 Java·SQL API 사용법만 설명한 경우에는 풀이 핵심 노출 여부를 보고 없음 또는 작은 힌트로 판정한다.
- 알고리즘 선택과 정확성은 사용자의 짧은 문장만으로 판정하지 않고 풀이 전 메모, 최종 코드와 제출 결과를 함께 본다. 코드가 선택한 알고리즘을 정확히 구현하고 기록한 흐름과 일치하면 세부 증명이 생략돼도 이해한 것으로 본다.
- DP의 상태·점화식, 그래프 탐색의 방문·이동, 그리디의 선택 안전성, 이분 탐색의 범위 축소, 일반 반복의 불변식 등은 Codex가 학습 피드백으로 보완한다. 사용자가 틀린 근거를 제시하거나 코드가 우연히 통과한 정황이 있거나 확인 질문에도 핵심을 설명하지 못한 경우에만 등급 하향 근거로 사용한다.
- A등급 조건을 모두 충족하지 못한 성공 문제는 C등급 사유가 없는 한 B등급으로 판정한다. 따라서 A·B·C 사이에 미분류 구간을 두지 않는다.
- 2026-10-07부터 정답성 설명은 엄밀한 서술 시험이 아니라 학습 보조다. 목표 시간 내 무힌트 첫 제출 성공이고 코드·설계가 일관되면 기본적으로 A로 판정하며, 빠진 세부 설명은 등급 감점 대신 필요한 D+3 짧은 회상이나 풀이 직후 피드백으로 보완한다.
- D+7 변형 전이 성공은 연결된 원본과 같은 핵심 유형의 처음 보는 문제를 핵심 힌트·해설·정답 코드 없이 성공한 경우다. 작은 힌트를 사용한 성공은 별도로 기록하되 전이 성공률의 성공 건수에는 포함하지 않는다.

### 출제 의도와 실제 풀이 비교

- 정답 안정성 A·B·C 등급과 출제 의도 알고리즘 학습 여부는 분리해서 평가한다. 공식·추천 의도와 다른 방법을 사용했다는 사실만으로 등급을 낮추지 않는다.
- Codex는 문제를 추천할 때 목표 알고리즘을 정할 수 있지만 풀이 전에는 공식 출제 의도와 Codex 목표 알고리즘을 사용자에게 노출하거나 보이는 `review.md`에 미리 채우지 않는다.
- 사용자는 풀이 직후 Codex의 설명을 보기 전에 `실제 사용 알고리즘`과 `출제 의도라고 생각한 알고리즘`을 작성한다.
- 풀이가 끝난 뒤 Codex는 `공식 출제 의도 알고리즘`, `Codex 추천 목표 알고리즘`, 실제 사용 알고리즘을 비교한다. 플랫폼이 의도를 명시하지 않았다면 추측하지 않고 `공식 의도 명시 없음`으로 기록한다.
- 공식 의도 일치 여부와 Codex 목표 일치 여부를 각각 `일치 / 유효한 대안 / 보완 필요 / 의도·목표 명시 없음`으로 기록한다.
- 의도와 같고 근거가 명확하면 추가 학습을 하지 않는다.
- 다른 방법이지만 정확하고 제한을 충분히 만족하면 유효한 대안으로 인정한다. 풀이 완료 피드백에서 의도 알고리즘의 핵심 신호, 풀이 흐름 또는 의사코드, 복잡도와 실제 풀이와의 차이를 즉시 3~5분 분량으로 설명한다.
- 정답이지만 현재 진도의 핵심 유형을 놓쳤다면 풀이 완료 시 의도 알고리즘의 의사코드와 필요한 예제 추적까지 즉시 설명한다.
- D+3에는 의도 알고리즘을 처음 공개하지 않는다. 풀이 완료 시 이미 배운 실제·의도 접근의 핵심 흐름, 복잡도, 장단점과 중요한 엣지 케이스를 코드 없이 회상·비교한다.
- 현재 방법이 제한에 간신히 통과하거나 의도 알고리즘보다 뚜렷하게 비효율적이면 풀이 완료 시 차이와 개선 방향을 즉시 설명하고, D+3에 두 방법의 비교 회상, 핵심 유형 또는 최근 취약 유형이면 D+7에 새로운 변형 문제를 편성한다.
- 현재 방법이 제한을 만족하지 못하면 결과와 A·B·C 기준에 따라 판정하고 해당 유형을 다시 학습한다.
- A등급 문제는 의도와 다른 유효한 대안으로 풀었더라도 동일 문제를 다시 구현하지 않는다. 필요한 학습은 짧은 설명·의사코드 또는 D+7의 새 변형으로 진행한다.
- 대안 학습 상태는 `불필요 / 설명 필요 / 의사코드 필요 / 변형 문제 필요 / 완료`로 기록한다.

### 풀이 후 학습 피드백

- 사용자가 문제를 풀었다고 알리면 풀이 전 메모, 최종 제출 코드, 제출 결과를 함께 본다. 결과만 보고 정답 코드를 제시하지 않고, 사용자가 처음 세운 가설과 실제 구현 사이에서 무엇을 잘 봤고 무엇을 놓쳤는지 먼저 분석한다.
- 다음 항목 중 실제 성장에 중요한 내용만 우선순위대로 1~3개 선택한다.
  1. 문제의 핵심 신호나 정답성 근거 중 놓친 부분
  2. 실제 풀이와 공식·추천 의도 알고리즘의 차이
  3. 시간·공간복잡도를 개선할 수 있는 알고리즘이나 자료구조
  4. 불필요한 연산·객체 생성을 줄이거나 안전성을 높이는 Java API와 구현 방식
  5. 다음 문제에도 재사용할 수 있는 사고 규칙
- 선택한 학습점은 `왜 필요한지`, `어떻게 동작하는지`, `현재 풀이와 복잡도·장단점이 어떻게 다른지`, `다음에는 어떤 신호로 떠올릴지`까지 설명한다. 코드가 필요한 경우에도 핵심 부분과 흐름을 함께 설명하며 코드만 제시하지 않는다.
- 다른 알고리즘이더라도 정확하고 제한을 충분히 만족하면 유효한 대안으로 인정하고 등급을 낮추지 않는다. 의도 풀이를 배우는 목적은 정답을 부정하는 것이 아니라 선택지를 늘리고 유형 인식을 강화하는 것이다.
- 사소한 이름·서식 취향이나 제한에서 의미 없는 미세 최적화는 필수 학습점으로 만들지 않는다. 빅오 개선, 오류 예방, 반복 가능한 Java 지식, 취약 유형 보완을 우선한다.
- 의미 있는 추가 학습이 없으면 `현재 풀이가 충분함`과 그 이유를 기록한다.
- 피드백 결과를 `review.md`의 `풀이 전 사고와 실제 코드의 차이`, `풀이 후 새로 배운 점`, `복습에 포함할 학습 포인트`에 남긴다.
- 새로 배운 내용은 설명으로 끝내지 않고 한 문장 재사용 규칙과 짧은 회상 질문으로 바꾼다. B등급은 D+1 또는 D+3, A등급은 필요한 D+3, 새로운 문제에 적용해야 확인되는 개념은 D+7 변형에 포함한다.

### 풀이 완료 직후 코드 개선 피드백

- 사용자가 문제를 풀었다고 알리면 Codex는 제출 코드를 직접 확인하고 실행·검증한 뒤 개선 가능성을 평가한다.
- 확인 범위는 시간·공간복잡도, 중복 연산, 불필요한 객체 생성, 더 적합한 Java 표준 API, 조건·반복·자료구조 단순화, 엣지 케이스 안전성과 가독성이다.
- 개선점은 `빅오 개선`, `상수 비용·메모리 개선`, `가독성·안전성 개선`으로 구분한다. 실제로 빅오가 같다면 더 빠른 알고리즘이라고 과장하지 않는다.
- 예를 들어 접두사 비교에서 `substring()`으로 새 문자열을 만든 뒤 `equals()`를 호출한 경우, `startsWith()`로 임시 문자열 생성을 피하고 길이 검사와 비교 의도를 한 번에 표현할 수 있음을 알려준다. 이 경우 점근 복잡도는 같고 객체 생성·가독성·안전성이 개선된다고 설명한다.
- 의미 있는 개선점이 있으면 원본의 일부 조각만 지적하고 끝내지 않고, 개선된 `solution` 전체 또는 독립적으로 이해 가능한 완결된 코드 예시를 문제별 `review.md`에 작성한다. 변경 이유, 복잡도 변화 여부와 다음 문제에 재사용할 기준도 함께 기록한다.
- 개선할 점이 없거나 현재 코드가 이미 충분히 적절하면 그 사실과 유지할 이유를 알려준다.
- 사용자가 요청하지 않는 한 원본 Java 코드는 수정하지 않는다. 개선 코드는 `review.md`의 Codex 분석에만 전체 예시로 기록하고, 대화에서는 핵심 개선점과 기록 위치만 알린다. 사용자가 대화에서 코드를 직접 요청한 경우에만 전체 예시를 보여준다. 사소한 취향 차이만 있을 때는 불필요한 재작성을 하지 않는다.

## 7. 실패 분류와 다음 추천

- 인식 실패: 적절한 알고리즘이나 자료구조를 떠올리지 못함
  - 같은 유형의 쉬운 변형을 우선 추천한다.
- 설계 실패: 유형은 알았지만 상태, 점화식 또는 자료구조 설계를 잘못함
  - 상태 정의 연습 문제를 우선 추천한다.
- 구현 실패: 인덱스, 조건문, 자료형, Java API 또는 엣지 케이스 실수
  - 비슷한 난이도의 정확성 중심 문제를 우선 추천한다.
- 시간 관리 실패: 올바른 방향으로 접근했지만 제한시간 운영에 실패함
  - 같은 난이도의 시간 제한 연습과 중단 기준을 적용한다.

정답률만으로 실력 향상을 판단하지 않는다. 유형 인식, 설계 정확도, 구현 안정성, 풀이 속도와 새로운 변형으로의 전이를 함께 평가한다.

### 프로그래머스 문제 파일 사전 생성

- 사용자가 당일 프로그래머스 문제명과 링크를 전달하면 풀이 전에 `algorithm-study/daily/YYYY-MM-DD/문제명/` 폴더를 생성한다.
- 문제 폴더에 프로그래머스 초기 `solution` 메서드 시그니처를 가진 `문제명.java`와 미작성 `review.md`를 둔다.
- `review.md`는 Codex가 미리 채우는 문제 정보·시간 배분, 사용자가 짧게 채우는 풀이 전 핵심 기록·풀이 후 결과, Codex가 기록을 마무리하는 분석으로 구분한다.
- 2026-11-02부터 사용자는 목표 시간 비율별 중립 질문 바로 아래에 각 한두 문장으로 답하고, 풀이 후에는 시간·결과·제출·설계 확정 시간·구현 실수·막힌 점만 기록한다. 체크박스와 완료 문장은 사용하지 않으며 힌트 수준은 Codex가 대화 기록으로 작성한다.
- Java 파일은 문제명의 공백을 밑줄로 바꾼 파일명과 동일한 `public class 문제명`을 사용하고, 상단에 `// 프로그래머스 Lv.N` 형식의 난이도 주석과 로컬 실행용 `main` 메서드를 둔다.
- `main`에는 문제에 공개된 입출력 예시를 호출하는 코드만 넣고, 정답·알고리즘·힌트는 미리 작성하지 않는다.
- Codex가 현재 체감 실력, 해당 문제의 레벨·유형·구현량, 1번·2번 문제의 역할, 최근 성공률·중앙 풀이 시간·실패 유형을 종합해 목표 시간을 정하고 `review.md`에 미리 기록한다.
- Codex는 목표 시간을 문제 이해·제한 20%, 단순 풀이·병목 20%, 접근 선택·풀이 흐름·정확성 20%, 구현 25%, 검증·제출 15%로 나눠 단계별 분량과 누적 종료 시점을 `review.md`에 미리 기록한다.
- 목표 시간은 문제를 처음 읽기 시작한 시점부터 제출 성공까지로 측정하며, 누적 결과에 따라 5분 단위로 조정한다.
- IntelliJ에서는 `algorithm-study` Java 모듈 하나만 사용하고, 새 문제 폴더를 `.idea/algorithm-study.iml`의 소스 루트로 추가한다. 모듈은 프로젝트 SDK `temurin-21`을 상속한다.
- 같은 문제 폴더나 파일이 이미 존재하면 덮어쓰거나 수정하지 않고 사용자에게 알린다.
- ChatGPT 예약 작업과 Codex는 자동 동기화되지 않으므로 사용자가 문제명과 링크를 Codex에도 전달해야 한다.

### SQL 문제 파일 사전 생성

- SQL 문제는 `daily/YYYY-MM-DD/sql/문제명/`에 저장한다.
- `solution.sql`에는 난이도와 `MySQL` 주석만 넣고 정답이나 쿼리 구조는 미리 작성하지 않는다.
- `review.md`는 `templates/sql-review.md`를 사용한다.
- SQL은 공식 테이블과 데이터가 프로그래머스에 있으므로 로컬 실행 환경을 강제하지 않고 플랫폼 실행·제출 결과로 검증한다.
- SQL 풀이가 끝나면 결과 행의 단위, JOIN으로 늘어날 수 있는 행, NULL과 중복 영향을 우선 확인한다.

등급 판정이나 객관 지표 계산에 반드시 필요한 정보가 빠졌거나 모호할 때만 추측하지 않고 누락 질문을 한 번에 모아 확인한다. 선택 항목이나 Codex가 분석할 항목의 빈칸만으로 기록 완료를 막지 않는다.

## 10. Codex의 일일 처리 절차

1. 해당 날짜의 Java 코드, SQL 쿼리와 사용자 회고를 확인한다.
2. 필수 정보가 모두 있는지 검사한다.
3. 누락되거나 모호한 정보를 사용자에게 한 번에 질문한다.
4. 사용자 답변을 받은 뒤 문제별 `review.md`를 완성한다.
5. 풀이 전 메모와 실제 제출 코드를 비교해 처음의 가설이 구현에서 어떻게 이어졌고 무엇을 놓쳤는지 확인한다.
6. 사용자가 피드백 전에 작성한 의도 알고리즘 추측과 실제 사용 알고리즘을 확인한다.
7. 정답성 근거, 공식·추천 의도와의 차이, 복잡도, 자료구조, 불필요한 연산·객체 생성, Java API와 안전성 중 중요한 학습점 1~3개를 골라 즉시 설명한다. 코드만 제시하지 않고 원리·복잡도·적용 신호까지 가르친다.
8. 새로 배운 내용을 한 문장 재사용 규칙과 회상 질문으로 정리해 `review.md`와 D+1·D+3·D+7 일정에 연결한다.
9. 각 문제를 A·B·C로 판정하고 판정 근거를 기록한다.
10. 알고리즘은 `metrics.csv`, SQL은 `sql-metrics.csv`에 문제별 정량 정보를 분리해 추가한다.
11. `dashboard.md`의 누적 지표와 취약 유형을 갱신한다.
12. 등급과 의도 알고리즘 학습 상태에 따라 D+1·D+3·D+7 및 재도전 일정을 갱신한다.
13. 사용자에게 당일 피드백을 제공한다.
14. SQL 결과는 `sql-metrics.csv`에 알고리즘 지표와 분리해 등급·문법·오류·복습 일정을 기록한다.
15. 날짜 폴더의 `README.md`에 그날 편성된 알고리즘 문제와 SQL 2문제의 결과·평가·복습 일정 및 ChatGPT 전달용 `[Codex 학습 요약]`을 기록한다.

사용자가 요청하지 않는 한 Java 원본 코드는 수정하지 않는다. 사용자 회고 원문과 Codex의 분석은 문서에서 명확하게 분리한다.

## 11. 객관적 평가 지표

- 총 풀이 수
- 첫 시도 성공률
- 목표 시간 달성률
- 실제 풀이 시간 중앙값
- 힌트·해설 의존률
- 인식·설계·구현·시간 관리 실패 비율
- 유형별 성공률과 풀이 시간
- D+3 재구현 성공률
- D+7 변형 문제 전이 성공률
- 같은 실수의 재발률
- A·B·C 등급별 누적 문제 수와 비율
- 출제 의도 알고리즘 사전 인식률
- Codex 목표 알고리즘 사전 인식률
- 유효한 대안 풀이 비율
- 의도 알고리즘 보완 완료율

등급 분포만으로 실력을 평가하지 않는다. 첫 시도 성공률, 목표 시간 달성률, 힌트·해설 의존률, 오류 유형과 D+7 변형 문제 전이 성공률을 함께 평가한다.

매주 6회 학습이 끝나면 다음을 포함한 주간 평가를 작성한다.

- 가장 향상된 유형
- 가장 취약한 유형
- 반복된 실패 원인
- 지난주 대비 변화
- 다음 주 우선 보완 항목
- 난이도 유지·상향·하향 의견

## 13. 자동화 상태

- 자동 문제 추천은 사용하지 않는다.
- 문제 추천은 사용자가 이 대화에서 명시적으로 요청한 경우에만 수행한다.
- 과거 `코딩테스트 일일 추천` 자동화는 중지 상태를 유지하며 다시 활성화하거나 새 예약 추천을 만들지 않는다.
